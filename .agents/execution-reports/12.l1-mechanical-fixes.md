## Fix 1 — Code-enforced default recall TTL for ALL non-standing theses

**Gap:** spec §2.1 gives the model `recall.max_age_min`, but only the FAILSAFE factory got a
code default (plan 11). A VALID low-conf / NEUTRAL thesis whose model-authored `max_age_min`
is 0/absent and whose recall events never fire otherwise waits forever — 07-02 diag: `th_04`
(NEUTRAL, LOW, `max_age_min=0`, `events=[]`) waited **20.5h** (1234 min) to session end.

**Fix.** New single-source constant `DEFAULT_LOWCONF_RECALL_MAX_AGE_MIN = 60` + pure helper
`effective_recall_max_age(declared, default=60)` in `agent/contracts/schemas.py`, adjacent to
`FAILSAFE_RECALL_MAX_AGE_MIN`. Semantics: `min(declared, default)` when declared is a positive
number, else `default` — a missing/zero/negative/oversized declared value → default; a smaller
declared value is respected (the model may ask to be re-called sooner); the default doubles as
the cap.

- **Executor (`agent/executor/trade_director.py`):** new `_lowconf_ttl_expired`, used only by
  `_maybe_recall_l1` (the THESIS_LOW_CONF re-ask). The standing-decision hard-expiry path
  (`_ttl_expired`, used by `_thesis_ttl_expired` / plan / WAIT) is UNCHANGED — spec §5 "no
  change to standing-thesis TTL tiers".
- **Bench (`agent/bench/run_bench.py`):** `_enforce_default_recall()` bakes the clamped
  `recall.max_age_min` into the logged thesis in `make_live_provider` (valid-thesis path).

**Divergence + rationale (replay fidelity).** The plan's wording put the clamp in
`lifecycle._run_waiting`. I applied it at GENERATION time (the provider) instead, because the
bench engine + `rescore` REPLAY logged decisions through `_run_waiting`; a clamp there would
retroactively rewrite the lifecycle boundaries of already-logged runs on rescore (e.g. `th_04`
would newly die at +60 instead of session end), breaking the plan's REQUIRED replay fidelity
("rescore is a scoring replay of logged behavior, not a re-simulation"). Baking the clamped
value into the logged thesis makes the default TTL manifest **only in NEW runs**, while rescore
of prior runs (whose logged `max_age` is untouched) stays byte-stable. The executor clamps at
runtime (no logging/replay concern there). Observable behavior is identical to the plan's intent
(a valid low-conf thesis re-calls at the default); the placement is what preserves fidelity.

**Verification (Fix 1):**
- Stub 2-date run: valid NEUTRAL/LOW theses now re-call at exactly **60 min** (`cause=recall`,
  `time_alive=60.0`; logged `recall.max_age_min=60`) instead of spanning the session; both stub
  runs byte-identical (deterministic).
- Rescore of `test_0702_run2_diag`: `th_04` stays **`session_end` @16:59:00** (NOT +60) — proof
  the fix does not rewrite prior runs.

## Fix 2 — Wrong-side / race DOL (th_02)

**Root cause (stated explicitly): a FRESHNESS/PROXIMITY RACE, not a menu side-filter bug nor a
validator gap.** Investigation of the logged `th_20260702_02` (decisions.jsonl + lifecycles.jsonl):

- At facts build (~20:00 ET) `now_price ≈ 30010` (session low 30010.0; the reasoning notes price
  had tested `prev1_day_low` @30009.25 to within 0.75 pts). The DOL `prev1_day_low` sat **0.75 pts
  BELOW price** — a correct-side, unswept below-pool, so the S8 DOL menu **correctly** offered it
  (logged `dol_menu_hit=true, dol_menu_id=D1`) and the validator **correctly** passed it (DOL on
  the DOWN bias side of price). Neither (a) menu side-filter nor (b) validator side-check was at
  fault at build time.
- Between the facts snapshot and the thesis's arrival (`born 20:01` + 90 s latency → arrival
  20:02:30, `arrival_price 29966.25`), price fell ~44 pts, **crossing below the DOL**. Because the
  lifecycle evaluates the DOL-touch at the arrival bar and price was already beyond it, the
  exhaustion (`price_beyond(30009.25, below)`) was satisfied immediately → a bogus **2-minute
  "completed"** on a level the thesis never actually drew to. That is case (c), the race.

**Fix (all three layers, per the plan — the menu guard is what actually fixes th_02; the other
two are belt-and-suspenders):**
- **Menu proximity guard** (`agent/derive_facts.py` `_dol_menu`, constant
  `DOL_MIN_DRAW_DISTANCE_PTS = 5.0`): a candidate DOL nearer than the guard to `now_price` is
  excluded — price is already sitting on it, so there is no forward draw and any latency crossing
  is a bogus completion. This is the layer that removes `th_02`'s D1 (0.75 pts away). Conservative
  by design (catches the already-at-the-pool case without over-excluding legitimate near-term
  targets).
- **Validator `SEM_DOL_WRONG_SIDE`** (`agent/contracts/validate_contracts.py` `_semantic_thesis`):
  a directional thesis's DOL must sit on the bias side of `facts.now_price` (UP above / DOWN
  below), else hard-reject — so the class can never pass validation regardless of menu
  correctness.
- **Scoring `suspect_completion`** (`agent/bench/score.py`): a `completed` directional lifecycle
  whose signed draw-distance at arrival is ≤ 0 (DOL already reached) AND that completed within
  `SUSPECT_COMPLETION_MAX_MIN = 5` min of arrival is flagged, plus a `suspect_completion_count`
  metric. Additive telemetry only — `completion_rate` is deliberately untouched so rescore of
  prior runs stays value-stable; the flag is the substrate for excluding these later.
  `agent/bench/report.py` renders both.

**Verification (Fix 2):**
- Root-cause regression (`agent/test_menus.py::test_th_02_root_cause_regression_dol_absent`,
  $0): the verbatim logged th_02 level snapshot fed through the menu builder no longer offers
  `prev1_day_low` as a DOWN DOL, while the genuine farther `prev2_day_low` (74.75 pts) IS still
  offered — targeted, not blunt.
- Rescore of `test_0702_run2_diag`: `th_02` is now flagged **`suspect_completion=True`** with its
  cause/boundaries unchanged (`completed @20:03:00`); `th_01` (real 88.5-pt draw) → `False`.

## Divergences from the plan
1. **Fix 1 clamp placement:** applied at decision-generation (bench provider) + executor runtime
   rather than literally in `lifecycle._run_waiting` — REQUIRED to keep `rescore` of prior runs
   byte-stable (see Fix 1 rationale). Observable behavior is the plan's intent; `_run_waiting` is
   untouched, so all existing lifecycle tests stay green.
2. **DOL proximity guard is a fixed constant (`DOL_MIN_DRAW_DISTANCE_PTS = 5.0`)** rather than a
   per-tier depletion threshold. A per-tier guard (session 20 / day 40 / week 80) would have
   excluded legitimate near-term targets and broke the existing synthetic menu fixtures (pools at
   dist 10); the fixed guard cleanly excludes the degenerate th_02 case (0.75 pts) while keeping
   the real DOLs in that session (49–75 pts) and the residual latency race is covered by
   `SEM_DOL_WRONG_SIDE` + `suspect_completion`.

## Tuning constants (conscious choices)
- `DOL_MIN_DRAW_DISTANCE_PTS = 5.0` and `SUSPECT_COMPLETION_MAX_MIN = 5.0` are deliberately
  CONSERVATIVE tuning knobs — chosen to catch the degenerate th_02 case (DOL 0.75 pts away,
  completion 0.5 min after arrival) without over-excluding legitimate near-term targets or
  over-flagging real fast completions. They are single-named constants, easy to retune once
  primary-mode runs accumulate.
- The proximity guard is scoped to the **DOL menu** (`_dol_menu`) only, NOT the predicate-target
  menu — the DOL is the draw a directional thesis commits to and the level the exhaustion fires
  on, so it is where the race manifests; falsification/anti-pool predicate targets are a
  different concern and intentionally left unguarded.

## Risks / follow-ups
- The proximity guard fixes the menu-origin of th_02; a DOL that is farther than the guard at
  build but still crossed within the latency window would not be excluded at build — it is caught
  post-hoc by `suspect_completion` (for metrics exclusion) but still produces a short lifecycle.
  A larger guard would over-exclude; the current split (small menu guard + telemetry) is the
  intended balance. Revisit if suspect_completion counts stay non-trivial in future runs.
