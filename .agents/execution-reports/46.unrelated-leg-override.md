## Challenges & Resolutions

**Challenge 1: Arm-1 computed twice in most non-forced Analyzer branches**
- **Issue:** `_premove_route`/`_premove_route_inner` computed `_override_thesis` once for diagnostics; `Analyzer._call` then recomputed it again in `shadow` mode and in the `NOT_BIG`/`NO_LEG`/`UNKNOWN` branches under `"on"` mode.
- **Root Cause:** The route helper's diagnostic computation and `_call`'s own arm-1 call were not wired to share a result.
- **Resolution:** Changed the route functions to return `(forced, arm1)` and had `_call` reuse the returned `arm1` instead of recomputing it.
- **Time Lost:** Not separately tracked; caught during code review, fixed and re-verified in the same pass.
- **Prevention:** When a helper computes a value for diagnostics that the caller also needs for control flow, return it rather than letting the caller recompute — an easy miss when the "diagnostics" framing hides that the value is load-bearing elsewhere.

**Challenge 2: Two different "mid" values with the same informal name**
- **Issue:** `_premove_thesis`'s original docstring described "the mid" without distinguishing the DOL's frozen 09:20-boundary mid (`pm.mid_at_boundary()`, record-only) from the Executor's actual take-profit mid (recomputed from the leg's extreme extended to the fill).
- **Root Cause:** Both values are legitimately called "the mid" in different parts of the pipeline, and the plan's own §1a text uses "mid_0920" and "leg mid" somewhat interchangeably.
- **Resolution:** Expanded the docstring to name both explicitly and state that they can differ, pointing to `Executor._premove_mid_pick`/`_track_premove_extreme` as the actual take-profit source.
- **Time Lost:** Minimal; documentation-only fix.
- **Prevention:** When a plan introduces two related-but-distinct computed values with informally overlapping names, the module docstrings should name them explicitly from the start.
