## Findings

```
severity: medium
file: smt_detect.py
line: 335-338
issue: float(e.get("fire_price", e.get("price", 0.0))) raises TypeError for a fill whose fire_price key exists but is None — and the raise aborts the WHOLE ingest, not just the bad entry.
detail: For a fill, _detect_state_fill_entries always emits the key "fire_price": st.get("fire_price"). dict.get(key, default) returns the stored None (not the default) when the key is present, so the fallback to e.get("price") (always None for fills) never engages, and float(None) raises. This math is OUTSIDE the try/except (the try at L322 closes at L325). revalidate_and_filter_pending has no per-entry guard around this block, and its only caller (_ingest_pending_smts, session_pipeline.py L2476-2477) wraps the entire call in `except: pass` — so one corrupt fill state would discard ALL carried survivors for that cold start, silently. Not reachable via the normal producer path (fire_price is always set at the same moment as the fire flags, L1040/L1067; the re-arm at L1003-1008 never clears it), so this is defense-in-depth against a malformed/legacy-version state, not a live bug.
suggestion: Guard the fulfillment math per-entry, e.g. wrap L333-358 in try/except (continue/keep on failure) OR coerce fire_price defensively: `_fp = e.get("fire_price"); if _fp is None: _fp = e.get("price"); if _fp is None: # skip revalidation, keep as survivor`. Mirrors the total/never-raise contract already claimed in the _detect_state_fill_entries docstring.
```

```
severity: low
file: session_pipeline.py
line: 2344-2401 (_detect_state_fill_entries)
issue: FILL carry does not exclude fills that were already fulfilled DURING the prior session at WRITE time, unlike the LEVEL carry which filters fulfilled/invalidated/superseded/retired_depleted (L2311-2313).
detail: This asymmetry is actually CORRECT — the fill lifecycle (detect_fill_smts) never sets a `fulfilled`/terminal flag on the fill state (init block L986-993 has no such field), so there is nothing to filter on, and fulfillment is re-derived at read time. The read-side revalidation window is (fire_time, session_open) (smt_detect.py L327), which spans the remainder of the prior session PLUS the overnight gap, so an in-session fulfillment IS caught as drop_fulfilled on cold start. The behavior is self-consistent; flagging only so a future reader does not "fix" the asymmetry by mistake. No change required.
suggestion: Optionally add a one-line comment at L2358-2360 noting fills carry every fired record because they have no in-session terminal flag, and fulfillment is re-derived by the wide revalidation window. Documentation only.
```

```
severity: low (informational — SHADOW guarantee)
file: hypothesis.py
line: 2217, 1497, 1548
issue: Carried FILL records DO feed direction. The "shadow" property is empirical (A/B), not architectural — and no A/B artifact / execution report for Phase 1.5 exists in-tree yet.
detail: The carry-write branch (session_pipeline.py L2114+) and the carried survivors appended to `smt_active_set` (L2464) are not isolated debug keys. hypothesis.py L2217 reads `divs = hypothesis.get("smt_active_set")`, passes divs to _determine_direction (L2231), which scores it via _compute_smt_score_v2(divs) (L1497) → smt_sc → _co_evaluate_with_smt (L1548) → direction confidence. A carried fill has tier="day" + a side, so it contributes ±_SMT_V2_TIER_WEIGHT["day"]=±2.0 to the directional score on the NEXT session's cold start. The pre-existing LEVEL carry already feeds this same path, so 1.5 adds fills to an already-live (not isolated) channel. The plan itself states the shadow property must be PROVEN by a byte-identical 1s/1m A/B vs HEAD 0250177 (plan acceptance b, L183-185: "Any trade diff = SMT is wired to direction somewhere → a FINDING"). That A/B has not been run/recorded — there is no execution report past Phase 1.3/1.1.5 and no regression artifact for 1.5.
suggestion: Block merge on the A/B. Because carried fills measurably change _compute_smt_score_v2, byte-identical trades are NOT obviously true a priori — if the prior session left any fired-unfulfilled fill, the next cold start's smt_score shifts, which CAN flip a borderline _co_evaluate_with_smt outcome. Run the 1s (and 1m) A/B on a contiguous pair where the first day leaves a fired fill, and confirm trades match exactly before accepting.
```

line: 1003-1008, 1041-1046, 1068-1072
issue: On re-arm, fire_phase / fire_time / fire_zone / fire_leader are not cleared; a fill that fired fill_b, then re-armed (fill_a_fired reset to False, fill_b_fired left True), still carries with stale fire_* metadata.

Low impact given the records are shadow.
suggestion: If exact fire-state fidelity matters for the carry, clear fire_phase/fire_time/fire_zone/fire_leader alongside fill_a_fired in the re-arm block (L1003-1008). Otherwise document that a re-armed-but-not-re-fired fill carries its last completed fire's metadata. Cosmetic for a shadow record.
