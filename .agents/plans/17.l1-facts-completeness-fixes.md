# L1 Facts-Completeness Fixes (session-liquidity scoping, P5 curation, mid HTF-verdict)

> **For agentic workers:** implement this plan end-to-end in `agent/derive_facts.py`
> (and its tests/fixtures). Leave all changes UNSTAGED — do not commit or push.

**Goal:** close three confirmed facts-pipeline gaps found during a multi-day root-cause
audit of wrong L1 thesis calls: (1) prior-session liquidity levels are offered as P1
targets long after they should be time-gated out of scope, (2) the P5 FVG-fill block is
an unfiltered, unverdicted 70-line dump the model never uses, (3) `daily_mid`/`weekly_mid`
carry no HTF-close verdict the way every other level does, so P4 (reclaim/failed-reclaim)
keeps getting mistyped as the weaker P3 or skipped entirely.

**Architecture:** all three fixes are additive to `agent/derive_facts.py`'s existing
facts-computation pipeline. Fix 3 and (the verdict half of) Fix 2 deliberately REUSE the
existing `_htf_close_status()` per-level machinery by treating `daily_mid`/`weekly_mid`
and each visited FVG zone's far edge as synthetic "levels" fed through the same function
— this means the existing S9 rendering loops need little to no new code, only new entries
populated into the dicts they already iterate.

**Tech Stack:** Python, pandas. No new dependencies.

## Fix 2: Curate + verdict the S9 FVG-fill (P5) candidates block

**Files:**
- Modify: `agent/derive_facts.py` — the FVG-zone data structure/computation (search for
  `fvg_zones`, `visited`, and the S6 rendering) and `render_evidence_text` (search for
  the FVG-fill section — check if one already exists in S9; if the FVG list currently
  only appears in S6 and not S9 at all, add a new S9 subsection for it, following the
  exact style of the existing "SMT candidates" subsection in the same function)
- Test: `agent/bench/test_facts.py`

**Problem:** S9's FVG-fill-relevant content today is an unfiltered restatement of the
entire S6 FVG list (confirmed: 70 lines spanning 10 days in one real example), with only
a binary VISITED/not-visited flag — no recency curation, no verdict. `render_evidence_text`
never surfaces any per-zone accept/reject read at all. Confirmed empirically: 0 of 12
real L1 runs this session ever declared a single P5 evidence item.

**Two changes needed, both additive to `render_evidence_text`'s FVG-related output (or a
new subsection there if none currently exists):**

1. **Recency curation.** Add a constant `FVG_LOOKBACK_DAYS = 3` near
   `SMT_LOOKBACK_HOURS = 24`. When rendering FVG-fill candidates for S9 (NOT S6 — S6 stays
   the full historical list, this curation is S9-only, mirroring how S9's SMT-candidate
   list is already a curated subset of the raw S3 sweep matrix), only include VISITED
   zones whose formation timestamp is within `now - FVG_LOOKBACK_DAYS` days of `now`.

2. **Held/violated verdict, reusing `_htf_close_status`.** For each zone included after
   curation, determine whether the fill was HELD (zone acted as support/resistance, held)
   or VIOLATED (price closed decisively through it) since being visited, using the SAME
   `_htf_close_status()` function already used for named levels:
   - For a **bull** zone: call `_htf_close_status(df, swept_at=<zone's visit timestamp>,
     price=<zone's LOW edge>, side="below", now=now)`. A `"beyond": True` result on
     either timeframe means price closed BELOW the zone's low edge since the visit —
     VIOLATED (maps to P5 `direction: reject`). No qualifying close, or all closes stay
     above the low edge — HELD (maps to `direction: accept`).
   - For a **bear** zone: call `_htf_close_status(df, swept_at=<zone's visit timestamp>,
     price=<zone's HIGH edge>, side="above", now=now)`. `"beyond": True` on either
     timeframe = VIOLATED (`reject`); otherwise HELD (`accept`).
   - Use the 1h result if available; fall back to 4h if 1h is immature; if both are
     `None` (no qualifying close yet since the visit), render the zone as
     `(fill too recent to verdict)` rather than guessing.
   - Render format, one line per curated zone, following the existing FVG line style
     seen in S6 (`f"{tkr} {tf}hr {zone_ts} {kind} zone {lo}-{hi} -> VISITED"`) extended
     with the verdict: append ` -> HELD (accept)` or ` -> VIOLATED (reject)` or
     ` -> (fill too recent to verdict)`.

**Test cases** (add to `agent/bench/test_facts.py`), using real dates already confirmed
this session to have genuine visited zones:
1. `2026-07-20 09:20 ET`: assert the curated S9 FVG list includes
   `MNQ 1hr 2026-07-16 21:00 bear` and `MES 1hr 2026-07-16 21:00 bear` (both confirmed
   real, visited, bear-kind this session) — WAIT: 2026-07-16 is 4 days before 2026-07-20,
   outside a 3-day lookback. Before writing this test, actually run the fix against this
   boundary and see which zones survive the 3-day window; if the specific example zones
   from the earlier investigation fall outside the window, that's fine — pick whichever
   zones DO survive curation at this boundary for the assertion, and separately assert
   that a zone known to be >3 days old is correctly EXCLUDED (curation is doing something).
2. Assert a zone with NO subsequent qualifying HTF close renders `(fill too recent to
   verdict)`, not a false HELD.
3. Assert the S6 raw list is completely unchanged by this fix (curation is S9-only).

**Design note for the implementer:** if `FVG_LOOKBACK_DAYS = 3` produces an empty or
near-empty curated list at several of the test boundaries (i.e. 3 days turns out too

## Fix 3: HTF-close verdict for `daily_mid`/`weekly_mid`

**Files:**
- Modify: `agent/derive_facts.py` — wherever `bundle.htf_close_status[tkr]` and
  `bundle.swept_at[tkr]` get populated per named level (search for where
  `_htf_close_status(` is called in a per-level loop, likely near where `bundle.levels`
  is iterated to build these two dicts)
- Test: `agent/bench/test_facts.py`

**Problem:** confirmed 3-for-3 across real dates (2026-07-20, 2026-07-22, 2026-07-27):
`weekly_mid` renders in S9 as a single bare number (`weekly_mid = 29031.75`) with NO
`[1h]`/`[4h]: close=X -> REJECTED/ACCEPTED` verdict line the way every named swept level
gets. This is the most plausible reason P4 (HTF-confirmed reclaim/failed-reclaim) keeps
getting mistyped as the weaker P3 (bare position) or skipped: there's no ready-made fact
to anchor a P4 declaration on for the mid, unlike every other level. `daily_mid` has the
exact same gap AND doesn't even get a bare-number line in S9 today (only `weekly_mid`
does) — fix both symmetrically.

**Implementation — treat `daily_mid` and `weekly_mid` as synthetic per-asset "levels"
fed through the EXISTING `_htf_close_status()` function, so the EXISTING S9 rendering
loop (`for name, tf_map in status.items(): ...` in `render_evidence_text`) picks them up
automatically with no new rendering code:**

1. For each ticker `tkr` in `("MNQ", "MES")`, compute the relevant mid value:
   `daily_mid` — use `bundle.day_hi[tkr]`/`bundle.day_lo[tkr]` (already computed
   per-asset, per `bundle.day_hi[tkr] = float(dh_ext)` etc.) — `(day_hi[tkr] +
   day_lo[tkr]) / 2`. `weekly_mid` — use `bundle.week_hi[tkr]`/`bundle.week_lo[tkr]`
   (already per-asset per the existing comment "unlike weekly_mid, which is MNQ-only" —
   confirm these exist for both tickers before using them; if `week_hi`/`week_lo` are
   only ever populated for specific tickers, compute the per-asset mid from whatever
   per-asset week-high/week-low source is actually available — read the surrounding
   code carefully rather than assuming).

2. Find the LAST crossing of that mid within a lookback window (reuse
   `SMT_LOOKBACK_HOURS = 24` — if that's too short in practice for the mid specifically,
   note it in your completion summary rather than silently changing the shared constant):
   over `df.loc[now - pd.Timedelta(hours=SMT_LOOKBACK_HOURS):now]`'s 1-minute (or
   whatever granularity `df` already is) close series, compute `sign(close - mid)` and
   find the LAST index where this sign differs from the previous bar's sign (a genuine
   crossing, not just noise sitting exactly at the mid — treat a close exactly equal to
   the mid as continuing the previous sign, don't treat equality as its own crossing).
   That timestamp is the synthetic `swept_at`. The `side` to pass to
   `_htf_close_status` is `"above"` if the CURRENT (most recent) close in that window is
   above the mid, else `"below"` — i.e. the side price crossed TO, so a subsequent
   qualifying close confirming that same side reads ACCEPTED (a held reclaim) and a
   close back on the other side reads REJECTED (a failed reclaim) — this is exactly the
   P4 accept/reject semantic.
   - If no crossing is found in the lookback window (price has stayed on one side the
     whole time), leave this synthetic level's `swept_at` as `None` — same "never swept,
     not evidence" treatment the rendering loop already gives real levels with no sweep.

3. Populate `bundle.swept_at[tkr]["daily_mid"]` / `["weekly_mid"]` and
   `bundle.htf_close_status[tkr]["daily_mid"]` / `["weekly_mid"]` (via
   `_htf_close_status(df, swept_at=<computed>, price=mid, side=<computed>, now=now)`)
   the same way every other level in that per-ticker loop already does.
   `render_evidence_text`'s existing loop iterates `status.items()` and will render these
   automatically once populated — do NOT add new print statements for this, verify the
   existing loop produces sensible output for these two new entries and stop there.
   (The nested/duplicate/P2-suppression tagging logic in that loop keys off
   `bundle.suppressed_p1_levels` and `bundle.smt_candidates` — `daily_mid`/`weekly_mid`
   won't appear in either, so those tags should naturally stay empty for these two
   entries; confirm this rather than assuming.)

4. Keep the existing `A(f"weekly_mid = {bundle.weekly_mid}")` bare-number line as-is (it's
   the MNQ running scalar, used elsewhere) — this fix ADDS the per-asset HTF-verdict
   lines alongside it, doesn't replace it. Add a symmetric `A(f"daily_mid = {bundle.day_mid}")`
   bare-number line next to it if one does't already exist (check first).

**Test cases** (add to `agent/bench/test_facts.py`):
1. `2026-07-27 09:20 ET`: assert `bundle.htf_close_status["MNQ"]["weekly_mid"]["1h"]` is
   not None and its `"beyond"` is `False` (REJECTED) — this matches the confirmed real
   finding (MNQ's 1h closes sat below its weekly mid for 4 consecutive bars despite
   wicking above intrabar, right before this call).
2. `2026-07-22 09:20 ET`: assert `bundle.htf_close_status["MNQ"]["weekly_mid"]["1h"]["beyond"]`
   is `True` (ACCEPTED — this was the confirmed real HTF-reclaim-from-below case) and the
   same for `MES`.
3. A boundary where the mid has NOT been crossed recently (pick one from the 10-day
   sample where the earlier investigation didn't find mid-related evidence, or construct
   one by checking): assert the synthetic level's status comes back `None`/immature
   rather than a fabricated verdict.
