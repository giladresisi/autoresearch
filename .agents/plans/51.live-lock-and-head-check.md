# Plan 51 — `trade.py start` guards for a two-machine setup: R2 live lock, stale-data check, HEAD check

Complexity: ⚠️ Medium. One new section in `scripts/r2_sync.py`, one new `trade.py` subcommand, guards inside the
`trade.py start` branch. No change to the trading path (`agent/`, `automation/`, `orchestrator/`).

**EXECUTION RULES — READ FIRST:** implement ALL of this plan; leave ALL changes UNSTAGED (no `git add`, no commit, no
push, no `git stash`); never call `publish` / `sync` / `promote` / `start` against the real bucket or the real
`<global>` folder from tests (fake S3 client + tmp dirs only; the operator runs the live check); do not read or print

## 1. Context an implementer needs (read this before the code)

**The project.** `auto-co-trader` is a futures (MNQ/MES) trading system. A live orchestrator process
(`orchestrator.main` → `automation.main`) streams IB bars, an "agent" brain decides, and orders go to a broker through
PickMyTrade/Tradovate. All runtime data lives in a machine-global folder `<global>` (`paths.global_root()`, default
`~/projects/auto-co-trader/global`): `general/main` (parquets the backtests read), `general/live` (parquets the live
run appends to), `sessions/<date>/` (per-session files), `thesis_cache/`, `studies/`.

**What plan 50 (merged, PR #121) added.** The operator wants to run the live from more than one physical machine, one at
a time. `scripts/r2_sync.py` + `trade.py publish|sync` move `<global>` to/from a private Cloudflare R2 bucket
(S3-compatible, accessed with `boto3`; env `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` in the
gitignored `.env`). `trade.py promote`, `trade.py rollover-prep` and the `parquet-check --mode session-end` script call
`r2_sync.publish_after_promote()`, so a finished run lands in R2; the session-analysis skill's Step 0 and any other
machine run `trade.py sync` to pull it. Read `.agents/plans/50.r2-publish-sync.md` (decisions 3-14) and the module's
docstring first. Facts you will use:
- Groups `main`, `live`, `sessions`, `thesis_cache`, `logs`, `studies`; each has `manifest/<group>.json` in the bucket,
  written LAST, holding per-file `{size, sha256, last_ts}` plus `published_at`, `source_host`, `git_sha`, `MNQ_CONID`,
  `MES_CONID` (`_provenance()`).
- `<global>/.r2_state.json`: per object key, the sha256 this machine last synced/published (the "baton" rules).
- `r2_sync.sync(only=..., dry_run=True)` classifies every file (download / ahead-left-alone / conflict) and makes only
  read-only GETs. `_git_sha()` and `_git_contains(sha)` (`git merge-base --is-ancestor sha HEAD`) already exist.
- `trade.py`: `_load_env()`, `_r2_cli()`, `_publish_tail()`. `--force` on `trade.py` is a GLOBAL flag (position.json
  overrides) and on `start` it means `FORCE_RESET` (wipes `position.json`; the agent brain REFUSES to run when it is set,
  see the comment in the `start` branch). **It must not be reused for the new overrides** (decision 6).

**The problem this plan solves.** IB allows ONE login per account, so only one machine may run the live at a time.
Today nothing stops machine B from starting a live run (a) while A still holds the session, (b) on parquets that A has
since extended and published (B never ran `sync`), or (c) on older code than the code that produced the published data
(the thesis cache is keyed per date × code version, so a different commit silently misses recordings and can change
replay/live behaviour). IB only fails at connection time with a vague error, and (b)/(c) fail silently. Plan 50's
baton rule detects divergent PARQUETS after the fact; it cannot prevent them.

## 2. Decisions

1. **Live lock = one R2 object, `live_owner.json`** (bucket root, not part of any group; excluded from sync/publish
   walkers). JSON: `{"host", "started_at" (ET ISO), "session_date", "git_sha", "pid"}`.
   - **Acquire** (inside `trade.py start`, after every guard below passes and BEFORE the existing "kill existing
     orchestrator" step): absent → write it. Present with the SAME host → allowed (a restart after a crash, or the
     supervisor's `--resume` restart); refresh `started_at`. Present with a DIFFERENT host → REFUSE, message names the
     host, the age, and the two ways out: run `promote` on that machine (releases it), or `start --take-over`.
   - **Atomic acquire:** use S3 conditional put (`put_object(..., IfNoneMatch="*")`; needs `boto3>=1.35`-era support —
     check the installed version; R2 supports it for PutObject). Step 1 verifies this against a throwaway key in a
     scratch bucket prefix with a one-off script, NOT in the test suite. If R2 rejects the header, fall back to
     get-then-put (best-effort; acceptable for two hand-operated machines) and say so in the docstring.
   - **Release:** `r2_sync.publish_after_promote()` releases the lock after a SUCCESSFUL publish when the lock's host is
     this host (covers `trade.py promote`, `rollover-prep` and the parquet-check session-end path). A standalone
     `trade.py publish` does NOT release (it may run mid-week for other reasons). A failed publish leaves the lock.
   - **Manual control:** new subcommand `trade.py live-lock [status|release|take-over]` (NOT `unlock` — that name already
     means "unlock the hypothesis direction", `live_orders.unlock_direction()`). `status` prints the lock + age;
     `release` deletes it only if this host owns it, else needs `--take-over`; `take-over` rewrites it for this host.
     Stale locks (crashed machine) are cleared with `live-lock release --take-over` after the operator checks the age.
2. **Stale-data guard** (decision for `start`): when R2 is configured, run `r2_sync.sync(only="main,live", dry_run=True)`.
   REFUSE if it would download anything or reports a conflict ("this machine is behind R2 / diverged — run
   `trade.py sync` first"). Local files that are AHEAD of R2 do not block (this machine ran the previous session and
   has not promoted yet; the lock rule already catches a foreign owner).
3. **HEAD guard:** read `git_sha` from the `live` group manifest (publisher's HEAD). REFUSE unless it is the local HEAD or
   an ancestor of it (`_git_contains`). Newer local code is fine. A diverged branch, older code, or a tracked-file-dirty
   working tree (`git status --porcelain --untracked-files=no` non-empty) is refused. No `git_sha` in the manifest (an
   older publish) → warn and continue. The message prints both shas and the fix (`git pull`/`git rebase`/commit).
4. **Where the guards run:** only in `trade.py start` (the live). Not in `sync`, `publish`, `promote` or the analysis
   worktrees, so analysis machines and scratch worktrees are never blocked. Order inside `start`: existing `--force`
   refusal → NEW guards (stale-data, HEAD, lock acquire) → existing kill-and-launch. A guard failure exits 1 and touches
   no process, no file, no lock.
5. **R2 not configured → skip all three guards with one line** ("R2 not configured — two-machine guards skipped"), so
   the single-machine setup behaves exactly as today. **R2 configured but unreachable / manifest unreadable → REFUSE**
   (fail closed; a guard that fails open defeats its purpose) with the override below.
6. **Override flags for `start` (own flags, never `--force`):** `--take-over` (acquire the lock even if a foreign host
   holds it) and `--skip-r2-checks` (skip all three guards, e.g. the bucket is down on a trading morning). Both are
   printed in the usage text and recorded in one stdout line when used.
7. **Host identity:** `host = os.environ.get("ACT_HOST_ID") or socket.gethostname()` (new optional env var; makes tests
   and VMs deterministic; `_provenance()` uses the same helper so `source_host` and the lock agree).

## 8. Risks

- A stale lock after a crash blocks the other machine until `live-lock release --take-over`; the refusal message shows
  the lock's age so the operator can judge it.
- The dirty-tree refusal can annoy a worktree with local edits; it only applies to `start`, and `--skip-r2-checks`
  exists. If it proves too strict in practice, downgrade it to a warning.
- Env var added (final report must carry the "ACTION REQUIRED — Env vars changed" notice): optional `ACT_HOST_ID`.
