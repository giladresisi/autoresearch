# CHANGE A — structural/permissive SMT invalidation rework (`smt_detect.py`)

**This is the meat. It is detection-only and becomes COMMIT 1.** Files: `smt_detect.py` + its tests.

## A.2 Grounded design

### A.2.1 New fired-record lifecycle
A fired level-SMT record is **pending** until exactly one of:
1. **fulfilled** — block (a), `smt_detect.py:619-635`, UNCHANGED.
2. **superseded** — NEW (§A.2.3): a newer same-`rec_type`+same-`direction` record fired in a later/same batch (across ANY level/tier).
3. **depletion-backstop tripped** — EXTENDED latch (§A.2.4): the per-ticker depletion latch trips for the record's level+direction.

There is **no fire-close adverse-run invalidation** (§A.2.2 removes it).

### A.2.2 REMOVE the adverse-run invalidation pass
Delete the entire post-loop pass at `smt_detect.py:732-770` (the `for skey, st in list(state.items()): ... reason:"adverse_run"` block) and its preceding comment block (`:732-741`). After removal:
- `st["invalidated"]` is no longer set by adverse-run anywhere in `_detect_level_smts`. (Other code still reads `st.get("invalidated")` — `smt_status`/`fulfillment_status` at `smt_detect.py:994-1049`, the re-arm resets at `:657-670` and the post-pass at `:776-794` — these keep working; `invalidated` simply stays whatever the re-arm logic sets it to, which is `False` on fire/re-arm.)
- `state["__invalidations__"]` is no longer appended to by this mechanism. The KEY may legitimately never appear now. Downstream readers tolerate absence: `session_pipeline.py:2265` guards `if _inv and ...`; `smt_status` does not read the trail. **Leave the `smt_invalidations.json` mirror code (`session_pipeline.py:2259-2270`) in place** — it simply won't fire (out-of-scope file anyway; we touch only the 4 allowed files).
- **Do NOT delete** `_invalidate_pts` or the `INVALIDATE_PTS_*` constants (constraint). `pending_smt_terminal` still imports/uses `_invalidate_pts` until §A.2.5; after §A.2.5 the helper is dead but the constant stays defined (note in a comment that the adverse-run usage was removed in Phase 1.1.5).

### A.2.3 ADD supersession (NEW)
When new records fire in a batch, retire any OLDER still-pending fired state of the **same `rec_type` + same `direction`**, across ANY level/tier, as redundant — keep only the freshest same-direction fired record.

Implement as a post-loop pass (after the per-level loop, near the existing batch post-pass at `smt_detect.py:772-794`), gated on `if records:`. Algorithm:
- For each fresh record `r` in `records` this batch: let `d = r["direction"]`, `rt = r["type"]` (== `rec_type`), and `fresh_key = _record_key(r)`.
- Sweep `state` for level-SMT entries (`"|" in skey`, 3-part key, `_parts[2] == rec_type`) that are `fired and not fulfilled and not superseded`, with `_parts[1] == d`, and `skey != fresh_key` (do not supersede the just-fired record itself).
- Mark each `st["superseded"] = True` (the new terminal flag) and append one audit row to `state.setdefault("__supersessions__", []).append({"time": iso, "key": skey, "superseded_by": fresh_key, "ref_name": _parts[0], "direction": d, "type": rec_type})`.
- **Scope is any-same-direction** (user decision) — do NOT scope to same level.
- Like the adverse pass it removed, supersession is INFORMATIONAL: it sets a flag + appends a trail; it MUST NOT touch `records`, `fired`, `armed`, `fulfilled`, fire fields, or re-arm — so trades stay byte-identical and the records list is unchanged.
- A superseded record stays in `state` (so its re-arm/fire bookkeeping is intact) but is treated as TERMINAL by the active-set consumer and by the carry write (see §A.2.6).

> Initialize `superseded` in the `st` defaults dict (`smt_detect.py:604-616`, add `"superseded": False`). Clear it (`st["superseded"]=False`) on fire (`smt_detect.py:691-695` block) and on every re-arm reset (`:660-670`) so a re-armed/re-fired record is fresh again — mirror exactly how `invalidated` is reset there.

### A.2.4 EXTEND the depletion latch to mark the fired record terminal (structural backstop)
At the per-ticker depletion latch (`smt_detect.py:705-730`), when a latch flips for a `name`, ALSO mark the corresponding fired record(s) terminal. The latch is in the WICK pass (`if not body:`) and runs per `name` inside the per-level loop, so at flip time you know `name`, `direction` (the loop's `direction`), `tier`, `kind_cls`.

On a NEW flip (the `if (_ent["mnq"], _ent["mes"]) != _was:` branch, `smt_detect.py:725-730`):
- Compute the fired-record keys for THIS level+direction across both rec_types: `for _rt in ("wick","body"): _k = f"{_skey(name, direction)}|{_rt}"`. (Direction here is the loop `direction` for this `name`; the latch is direction-symmetric per the sub but the fired record we retire is the one matching the swept side's direction.)
- If `state.get(_k)` is a fired-open dict (`fired and not fulfilled`), set `st["retired_depleted"] = True` (the new terminal flag) and append to `state.setdefault("__level_retirements__", [...])` — REUSE the existing retirement append (extend the existing event dict at `:726-730` with `"retired_records": [keys...]` OR append a sibling event with `"reason":"depletion_backstop"`; prefer extending the existing event to avoid a second list entry per flip). Keep it informational (no records/fire/armed mutation).
- Note: the latch is per-`name` and the loop visits `name` once per bar for the active `direction`; a `*_high` → `direction="short"`, a `*_low` → `direction="long"` (`smt_detect.py:569`), so the retired record key uses that same `direction`. Document this in a comment.

> Initialize `retired_depleted` in the `st` defaults dict and clear it on fire + every re-arm reset, exactly like `superseded`.

### A.2.5 Align `pending_smt_terminal` to the new lifecycle (carry re-validation)
`pending_smt_terminal` (`smt_detect.py:168-200`) currently returns `"fulfilled"|"invalidated"|"unfulfilled"`. A CARRIED SMT must be re-killed ONLY by **fulfillment** (favorable `_fulfill_pts`) or the **depletion backstop** (price runs `_deplete_pts` beyond the LEVEL). The required change: **drop the adverse-run `invalidated` branch** so an overnight-gap adverse run no longer kills a carried SMT.

**Investigation of the depletion-backstop-at-carry option (grounded):** `pending_smt_terminal` measures from `fire_price` only — it does NOT receive the level price. The call site is the pure core `revalidate_and_filter_pending` (`smt_detect.py:306-354`), which has each entry's `e["price"]` (the swept LEVEL price — set by `_active_record_to_pending`, `session_pipeline.py:2283-2285`: `price = mnq_lvl_price`). So the level IS available at the call site even though it is not threaded into `pending_smt_terminal` today.

**Decision (lean = minimal, but correct):**
1. **Drop the adverse-run branch** in `pending_smt_terminal` — the REQUIRED change. New contract returns `"fulfilled"|"unfulfilled"` only:
   - long: `"fulfilled"` if `window_high >= fire_price + _fulfill_pts(tier,"mnq")`, else `"unfulfilled"`.
   - short: `"fulfilled"` if `window_low <= fire_price - _fulfill_pts(tier,"mnq")`, else `"unfulfilled"`.
   - Keep it total; unknown tier still falls back via `_fulfill_pts`. Stop importing/using `_invalidate_pts` here. Update the docstring (`:172-183`) to state the lifecycle change and that adverse-run no longer kills a carried SMT.
2. **Add the depletion backstop at carry** by threading the level price through the pure core (NOT into `pending_smt_terminal`, to keep that helper's signature stable for its unit tests — add the level check inline in `revalidate_and_filter_pending`). In `revalidate_and_filter_pending`, after the `pending_smt_terminal` call (`smt_detect.py:323-333`), add: if not fulfilled, compute the depletion-backstop test from `e["price"]` (level) using `_deplete_pts(tier,"mnq")`:
   - long (swept `*_low`): depleted if `window_low <= level - _deplete_pts(tier,"mnq")`.
   - short (swept `*_high`): depleted if `window_high >= level + _deplete_pts(tier,"mnq")`.
   - On depleted → drop with a NEW audit reason `"drop_depleted"`. (Replaces the old `"drop_invalidated"` reason for the carry path; `"drop_fulfilled"` and `"drop_age"`/`"drop_dedup"` are unchanged.)
   - Guard: only run when `e.get("price") is not None`; if absent, skip the backstop (keep — no evidence).

> This keeps `pending_smt_terminal` a pure 2-state fulfillment helper (its tests only need the invalidated cases removed) AND restores a structurally-correct overnight kill (depletion past the level), consistent with the live `_deplete_pts` latch. Document in `revalidate_and_filter_pending`'s docstring (`smt_detect.py:236-255`) the new step ordering: age-cap → fulfillment OR depletion-backstop → dedup → rebuild.

# CHANGE B — contiguous-range carry routing (`regression.py` + `backtest_smt.py` + maybe `smt_state.py`)

**This is harness-only and becomes COMMIT 2.** Files: `regression.py`, `backtest_smt.py`, optionally `smt_state.py` + their tests.

## B.2 Grounded design — candidate evaluation + DECISION

**Goal:** when `run_regression` is given a CONTIGUOUS business-day range, carry `_PENDING_STORE` across its dates, WITHOUT breaking: per-date run dirs/artifacts, per-date plotting, per-date baseline record/diff, per-date P&L reporting, and parallel-isolation (in-memory per-process; never write a shared on-disk `pending_smts.json` in backtest).

### Candidate (A) single-call
For a contiguous range token, call `run_backtest_v2(start, end)` ONCE and split its returned trades+events back to per-date for `run_regression`'s per-date post-processing.
- `run_backtest_v2` returns `{trades, events, metrics}` (`backtest_smt.py:1219`) AGGREGATED across the range (`all_trades`/`all_events` accumulate over the day loop, `:1266-1267`); metrics are whole-range. To restore per-date run dirs/baseline/plot/P&L, `run_regression` would have to re-split aggregated trades/events by date (events carry ISO `time`; trades would need a date key) AND `run_backtest_v2` ALREADY wrote per-date run dirs internally? **It does not** — `run_regression` writes the run dirs (`:143-153`), and the plot reads them. So (A) requires re-implementing per-date attribution + per-date metrics in `run_regression`. **Invasive**; high risk of changing per-date baseline/plot/P&L semantics.

### Candidate (B) flag — `reset_pending: bool = True` on `run_backtest_v2`
Add `reset_pending: bool = True`. When `False`, `run_backtest_v2` preserves `_PENDING_STORE` across its `set_in_memory_mode(True)` call. `run_regression` keeps its per-date loop, passing `reset_pending=False` on every date AFTER the first WHEN the dates form a contiguous business-day run.
- Keeps `run_regression`'s entire per-date structure (run dirs, baseline, plot, P&L) UNTOUCHED. The ONLY changes: a flag on `run_backtest_v2`, a save/restore of `_PENDING_STORE` around `set_in_memory_mode`, and contiguity detection in `run_regression`.
- Parallel-isolation preserved: still in-memory; `_PENDING_STORE` is process-local; no shared on-disk file.

**DECISION: Candidate (B).** Least invasive; preserves every per-date property by construction (it does not alter `run_regression`'s per-date loop body). (A) would force a re-attribution rewrite of the per-date baseline/plot/P&L path — exactly what must NOT break.

### B.2.1 `set_in_memory_mode` preserve hook (`smt_state.py`)
`set_in_memory_mode` (`smt_state.py:266-275`) unconditionally does `_PENDING_STORE = None`. Add a keyword:
```python
def set_in_memory_mode(enabled: bool, *, reset_pending: bool = True) -> None:
    global _IN_MEMORY, _hyp_cache, _hyp_cache_valid, _PENDING_STORE
    _IN_MEMORY = enabled
    _hyp_cache = None
    _hyp_cache_valid = False
    _STORE.clear()
    if reset_pending:
        _PENDING_STORE = None
```
- Default `reset_pending=True` → existing callers (tests, single `run_backtest_v2`) unchanged.
- When `reset_pending=False`, `_PENDING_STORE` is left intact across the mode (re)set so the prior date's carry survives into this call.
- Update the docstring/comment block (`:272-275`) to explain the new param.

### B.2.2 `run_backtest_v2` flag (`backtest_smt.py`)

### B.2.3 contiguity detection + flag wiring (`regression.py`)
In `run_regression` (`regression.py:135-136`), the per-date loop currently always calls `run_backtest_v2(date, date, ...)`. Change:
1. Precompute, for the expanded `dates` list, a boolean per index: `is_contiguous_with_prev[i]` = `dates[i]` is the next BUSINESS day after `dates[i-1]` (so Fri→Mon is contiguous; a gap or a non-business jump is not). Implement a helper, e.g.:
   ```python
   def _is_next_bday(prev: str, cur: str) -> bool:
       p = pd.Timestamp(prev); c = pd.Timestamp(cur)
       nxt = (p + pd.offsets.BDay(1)).normalize()
       return c.normalize() == nxt
   ```
   Use `pd.offsets.BDay` so Fri+1 = Mon. (Both `dates[i]` are `YYYY-MM-DD` strings from `_parse_date_tokens`.)
2. In the loop, pass `reset_pending=(i == 0 or not _is_next_bday(dates[i-1], dates[i]))`:
   ```python
   for i, date in enumerate(dates):
       _reset_pending = (i == 0) or not _is_next_bday(dates[i - 1], dates[i])
       result = run_backtest_v2(date, date, write_events=True, mode=mode,
                                started=started, reset_pending=_reset_pending)
   ```
   - First date: `reset_pending=True` (clean start).
   - A date that is the next business day after the previous: `reset_pending=False` → carries.
   - A non-contiguous explicit list (e.g. `[06-05, 06-10]`): the gap makes `_is_next_bday` False → `reset_pending=True` → does NOT carry across the gap. (Required semantics.)
3. **Important grounding note:** `_parse_date_tokens` expands an `A:B` range with `freq="D"` (CALENDAR days), so a range that spans a weekend yields Sat/Sun dates too. But `run_backtest_v2(date,date)` builds `pd.bdate_range(date,date)` (`backtest_smt.py:1264`) → a weekend date yields an EMPTY business-day range → no bars → the day is a no-op (the `if mnq_1m_today.empty: continue` at `:1316`, and the run dir is still created but with no trades). The contiguity helper uses `BDay`, so it correctly treats Fri→(Sat,Sun skipped)→Mon: but the expanded list will include Sat & Sun. The executor MUST decide how the weekend placeholders interact: simplest correct behavior = compute `_is_next_bday(prev_non_empty, cur)` against the previous date that actually HAD bars, OR pre-filter the expanded `dates` to business days before the loop. **Recommended: filter `dates` to business days** right after `_parse_date_tokens` for RANGE tokens (drop weekend dates), so the loop only sees business days and `_is_next_bday(dates[i-1],dates[i])` is exact for Fri→Mon. Preserve explicit non-range single-date tokens verbatim (do not filter a user-typed weekend date silently — but a weekend single date is already a no-op). Document the choice. (Filtering range-expanded weekends also avoids creating empty weekend run dirs.)
