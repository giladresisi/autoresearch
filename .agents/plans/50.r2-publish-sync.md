# Plan 50 — R2 publish / sync of the global data folder

Complexity: ⚠️ Medium. One new self-contained module, two `trade.py` subcommands, a hook in `trade.py promote`,
and a Step 0 in the session-analysis skill. No change to the live trading path.

## Goal

Machine A runs the live. When it runs `trade.py promote`, the promoted parquets (and the finished run's other
data) are written to a private Cloudflare R2 bucket, OVERRIDING the previous remote copies. Any other machine runs
`trade.py sync` (standalone, any time) and ends up with the same `general/main` AND `general/live` parquets,
session files and thesis cache in its own `<global>` — so it is ready to be the NEXT machine to run the live.
The session-analysis skill calls `trade.py sync` at its start; it does not contain sync logic of its own.
R2 holds FINISHED runs only (operator decision 2026-10-05): no mid-session snapshots, no live comments over R2.

If the machine that ran the live is the analysing machine, `sync` must NOT overwrite its own live parquets.

Out of scope: a VPS run (IB Gateway login, PMT reCAPTCHA, broker session), live comments over R2, moving
`orchestrator_*.log` / `data/live_position.json` out of the worktree.

## Decisions (made, with the reason)

1. **Module `scripts/r2_sync.py`, CLI `trade.py publish` / `trade.py sync`** — same pattern as
   `scripts/rollover_prep.py` / `trade.py rollover-prep`. Nothing under `agent/` or `automation/` imports it.
2. **`boto3>=1.34,<2` against the S3 endpoint** `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`, region
   `auto`. Env: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` (the bucket NAME).
   Masked placeholders in `.env.example`; `trade.py` must `load_dotenv()` before reading them (global CLAUDE.md
   ".env loading verification" — `os.environ` alone will not see `.env`).
3. **Groups (bucket prefixes), each with its own manifest written LAST:**

   | Group | Local source | Bucket prefix | In default publish | In default sync |
   |---|---|---|---|---|---|
   | `main` | `<global>/general/main/**` (incl. `2026-06/` `2026-09/` `2026-12/` subfolders + rollover ledger) | `general/main/` | yes | yes |
   | `live` | `<global>/general/live/` parquets (`MNQ/MES_1s`, `MNQ/MES_1m`) + `global.json` (ATH seed) | `general/live/` | yes | yes |
   | `sessions` | `<global>/sessions/<date>/**` | `sessions/<date>/` | yes | yes |
   | `thesis_cache` | the directory returned by `agent.trader.thesis_cache.cache_root()` (honours `ACT_THESIS_CACHE_DIR`; default `<global>/thesis_cache/`) | `thesis_cache/` | yes | yes |
   | `logs` | worktree-root `orchestrator_stdout.log`, `orchestrator_stderr.log`, `orchestrator_crash.log` | `logs/<publish-date>/` | yes | no |
   | `studies` | `<global>/studies/**` | `studies/` | **no — explicit `--only studies`** | no (explicit) |

   **Verified 2026-10-05:** `last_tick.json` is per-second run-in-progress state (read only by `live_orders._current_price`,
   10 s staleness) → EXCLUDED. `pending_smts.json` is the deliberate cross-session SMT carry (`smt_state.py:77`, written
   by `session_pipeline`, read at the next session's cold start) → INCLUDED in the `live` group.
   The `logs` group publishes at most the last 5 MB of each worktree log (`LOG_TAIL_BYTES`): `orchestrator_stderr.log` was
   945 MB from a 2026-09 crash loop.
   Exclude everywhere: `*.bak`, `*.preroll.bak`, `*.prefidelity.bak`, `*.tmp`, `*.promote.tmp`, `*.pid`,
   `last_tick.json`, `MNQ_1s_gaps_preview.parquet`. (`last_tick.json` is run-in-progress state; a next live run must not inherit a stale one.)
   Measured 2026-10-05: main 1.4 GB, live 950 MB, sessions 32 MB (108 dates), studies 62 MB, thesis_cache 364 KB.
   First publish ≈ 2.3 GB (the two parquet sets are near-identical right after a promote, so R2 stores both —
   storage is cheap, and the next live run needs the `live` set); later publishes upload only changed files.
   R2 has no egress fee.
4. **Manifest** `manifest/<group>.json`: `{path: {size, sha256, last_ts (parquets only)}}` + `published_at` + `source_host`. The sha256 is
   also stored as object metadata. R2 multipart ETags are not MD5, so ETag is never trusted. Local hashes are
   cached in `<global>/.r2_hash_cache.json` keyed by `(path, size, mtime_ns)` so a re-publish does not re-hash 2.3 GB.
5. **Atomic publish:** upload all changed objects first, manifest last. A reader that sees a new manifest sees a
   complete group; a publish that dies midway leaves the old manifest in place.
6. **Promotion stays local; publishing is one shared tail called after it.** `promote_live_to_main()`
   (`scripts/check_session_parquets.py:367`) copies live→main on THIS machine only (backs up the old file to `.bak`,
   atomic replace) and `trade.py promote` calls it directly (`trade.py:798`). It is NOT dead code and is NOT deleted:
   the live machine still has to build `main` from `live`, and `main` is exactly what gets published. On an analysing
   machine nothing promotes locally — `trade.py sync` pulls `main` and `live` from R2 as finished files.
   A new `r2_sync.publish_after_promote()` (default groups: main, live, sessions, thesis_cache, logs) is called by
   BOTH promote entry points, directly after `promote_live_to_main()`:
   - `trade.py promote` (`--no-publish` skips it);
   - `check_session_parquets.py --mode session-end` (line ~968, only on its existing success condition: merge
     succeeded). Its JSON report gains `promotion.publish_success` / `publish_error`; a failed publish raises the
     exit code to 2 like a failed promote.
   Why a shared function instead of check_session_parquets shelling out to `trade.py promote`: `trade.py` is a
   CLI whose subcommands are inline branches (no importable function), a subprocess would add a process spawn,
   `uv`/venv resolution and exit-code plumbing, and `promote` prints rollover banners the report already
   captures. Calling the same tail gives one publish behaviour and one place to test it.
   - R2 not configured → one line "R2 not configured — not published", exit 0 (promote works offline as before).
   - Upload fails → the local promote is NOT rolled back; error printed; exit non-zero.
   - Refuse the upload while the live orchestrator is running (`_orchestrator_pid()`); print the `main` row counts
     and last timestamps being sent.
   - `trade.py rollover-prep` (non-dry-run) calls the same tail too: it creates a new `main/<YYYY-MM>/` subfolder
     and rewrites `rollover_ledger.json`, which live in the `main` group, so a roll that is not published leaves the
     other machine on the old contract era.
7. **Baton rule — a per-machine state file prevents clobbering in both directions.** `<global>/.r2_state.json`
   records, per object key, the sha256 this machine last synced from / published to R2.
   For a file F with local hash L, last-synced hash S, remote hash R:
   - `L == R` → nothing to do.
   - **Parquets (`*.parquet`) decide by CONTENT, not by "changed since last sync":** compare the last index
     timestamp of the local file (`Tl`) with the remote's (`Tr`, recorded in the manifest as `last_ts` per parquet).
     * `Tl > Tr` → local is AHEAD (has data R2 lacks): `sync` leaves it alone; `publish` uploads it. This is the
       "analysing machine ran the live → do not overwrite its live parquets" case.
     * `Tl <= Tr` and `L != R` → R2 has everything the local file has (a truncated or older copy): the REMOTE
       WINS and replaces it. The replaced file is first moved to `<name>.r2prev` (one generation, overwritten next time).
     * Both sides have data the other lacks (`Tl > Tr` while `R != S`, i.e. the remote also moved since this
       machine last synced) → CONFLICT: skip, report both last timestamps, exit non-zero; `--force` picks a side
       (`sync --force` = remote wins, `publish --force` = local wins).
   - **Non-parquets:** `L == S` and `R != S` → pull; `L != S` and `R == S` → local ahead, leave it (publish uploads it);
     `L != S` and `R != S` → conflict as above. No state yet for F and a local file exists → remote wins.
   - No state yet for a parquet and a local file exists → the timestamp rule above applies unchanged.
   Parquets are append-only time series, so a true conflict can't be merged automatically.
8. **`sync` is standalone and additive:** read manifest → download missing/changed objects to `<name>.r2tmp` →
   verify size + sha256 → `os.replace`. Never deletes unless `--prune`. It never touches the machine's `.env`.
   It refuses to run while the live orchestrator is running on this machine (it would replace parquets the live
   process is appending to).
9. **Selectors:** `trade.py publish [--only g1,g2] [--date YYYY-MM-DD] [--dry-run] [--force]`;
   `trade.py sync [--only g1,g2] [--date YYYY-MM-DD] [--dry-run] [--prune] [--force]`. `--date` limits the
   `sessions` group. Default `sync` = main, live, sessions, thesis_cache (sessions are 32 MB total and additive,
   so a full default sync is cheap).
10. **session-analysis calls `trade.py sync` at its start.** New "Step 0" in `.claude/skills/session-analysis/SKILL.md`
    (before Step 1): run `python trade.py sync` from the project root; if it reports R2-not-configured or an
    unreachable bucket, say so and continue with the local data (never block the analysis); if it reports a
    conflict, stop and show it to the operator. No sync logic lives in the skill.
11. **Logs and `data/live_position.json` stay in the worktree.** The `run-orchestrator` skill greps
    `orchestrator_stdout.log` in the worktree for its milestones, so moving it would break that skill. `publish`
    uploads the logs as a `logs` group; `live_position.json` is only a restart tracker and is not published
    (analysis uses `position.json` in the session folder).
12. **Rollover:** `main/<YYYY-MM>/` subfolders and the ledger travel in ONE `main` manifest; a partial selector
    that splits them is not offered (a split set breaks the roll silently).

13. **Provenance in every manifest** (`manifest/<group>.json`): `git_sha` (publisher's HEAD), `MNQ_CONID`,
    `MES_CONID`, `source_host`. `sync` prints a WARNING (never blocks) when: the local `MNQ_CONID`/`MES_CONID`
    differ from the manifest's (a roll happened on the other machine — the roll's `.env` edit is manual and
    machine-local), or local HEAD is not the publisher's `git_sha` and does not contain it (thesis cache is keyed per
    date × code version, so a different commit silently misses recordings and can change replay results).
    The `.env` itself is never published (credentials).
14. **Two-machine checklist printed by `sync`** at the end of a run that pulled `main`/`live`: machine's own
    `.env` conids vs manifest, `git_sha` vs HEAD, and the manifest's `published_at` + `source_host`. One short block.

## Risks

- **Two writers:** the baton rule detects divergence but cannot prevent it. Procedure: the machine that ran the
  live runs `promote` (publishes) BEFORE the other machine starts its own live run, and that other machine runs
  `sync` right before starting.
- **IB session:** one IB login per account, so two machines can't run the live at once.
- **`.env` is machine-local and diverges.** After a contract roll the new `MNQ_CONID`/`MES_CONID` must be set by hand
  on every machine (decision 13 only warns). Same for `LIVE_TRADING`, `TRADING_CONTRACTS`, `ACT_*` flags and the
  broker/PMT credentials: the plan does not sync them on purpose.
- **Different commit on the two machines** changes behaviour and misses thesis recordings; decision 13 warns.
- **Absolute paths:** some `signals.log` files contain the author's `C:\Users\...` paths (text only, harmless); no JSON state
  file does. Manifest keys are POSIX-style relative paths so a Windows↔Linux sync round-trips.
- **Token scope:** the key is bucket-scoped Object Read & Write; analysis-only machines can use a Read-only key
  (then `publish` fails with an auth error, which is the intent).
- **Env vars added** (the final response must carry the "ACTION REQUIRED — Env vars changed" notice):
  `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`.
