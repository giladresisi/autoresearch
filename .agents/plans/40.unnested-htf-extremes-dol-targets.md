# 40. Unnested weekly/monthly/ATH extremes as DOL/target levels

**Complexity: ⚠️ Medium** (was 🔴 before the operator pinned Q1–Q5 on 2026-09-22). The code is one pure module, one loader, and a kwarg threaded through five call sites. What remains non-trivial:
- Live/replay parity: both paths read the same 1m parquets, with no lookahead.
- The T2 target is also the plan-death level, so a farther target changes more than the take-profit.

Source: session 2026-09-21 theme O9 (operator-proposed; see `<global>/sessions/2026-09-21/optimizations.md`). Worktree `live` @ `e65e4fa`. Planned read-only; every number below was measured against the real parquets and the production code.

Operator decisions (pinned 2026-09-22):
- **Recompute** on every startup from the 1m parquets (not a list persisted between runs).
- **Same source on both paths.** Live and replay both read the 1m parquet files (never the 1s→1m resample).
- **Per-asset start dates:** MNQ **2026-06-16** (its ATH; the window includes the Jul 29 low) and MES **2026-06-11** (its lowest low since May 5; the window includes the Aug 13 ATH). Both directions for both assets.
  - These dates come from the operator's (unadjusted) chart. The module reads the back-adjusted series, where eras shift by different cumulative roll gaps. So "ATH" there is just the window's max: MNQ's back-adjusted Jun 3 high (31400) outranks Jun 16, but it falls before the start and is excluded.
- **Unnested:** a level is dropped once a later bar trades beyond it.
- **Scope:** Executor T2 target selection at the fill only (Q4). L1 is out of scope: on non-override days L1's DOL is ignored, and on override days the target comes from the pre-09:20 move, not these levels.
- **Precedence:** an unnested HTF extreme on the plan's side suppresses the projection draw (Q1 = P1).
- **Accepted consequences:**
  - O8 (`e65e4fa`, projection stretch gates disarmed) stays. Until this feature lands, the projection target is acceptable (insights 1–2).
  - A far T2 is also a far plan-death level, which is preferred over a plan kept alive with no take-profit (insight 10).
- **Ignored:**
  - the `l2-target-selection.md` §6 prior (insight 5), judged not relevant to sparse HTF extremes;
  - the 14-vs-17-day live/replay history mismatch (insight 7).

## Step 0 verdict: RULE — the rule-level questions are pinned

All five are pinned by the operator (2026-09-22):
- Q1 and Q4 as recommended, with Q1 refined to count only floor-passing rows;
- Q2 and Q3 accepted as recommended;
- Q5 reversed: running week and month extremes are included. With no open rule-level ambiguity this is a RULE. It still ships behind a flag that is OFF by default and is adopted only after the Wave-3 A/B (protocol steps 3–8). The rule text goes in `l2-target-selection.md` (the T2 spec, new §7a), with a pointer row in `l2-mechanisms.md` §11.

- **Q1 — Projection precedence: P1 (pinned).** The projection draw is offered only if a direction has no BAND named pool **and** no unnested HTF extreme on that side. "Price discovery" means price is beyond every unnested HTF extreme in that direction. The HTF row then joins the menu nearest-first like any pool. On 09-21 that makes D1 the Aug 17 high 30639.50 instead of projection_up 30338.25.
- **Q2 — Period convention (adopted).** Trade date = ts + 7h; week = ISO week of the trade date; month = calendar month of the trade date. Month-only entries exist (e.g. July's 30855.5 formed Jun 30 20:00).
- **Q3 — Trades beyond, and dedupe (adopted).** A strictly-beyond wick drops the level. Equal prices are deduped: keep one entry (month > week, then most recent) and record the others as aliases.
- **Q4 — Scope: T2 at the fill only (pinned).** Excluded: the L1 menu, predicates, P1 evidence and the S1 text.
- **Q5 — Running period: INCLUDED (operator, 2026-09-22; this replaces the planner's "exclude" recommendation).** The running week and running month extremes on each side are T2 candidates at every fill.
  - Week = from its Sunday 18:00 open up to the fill; month = from its first trading date up to the fill.
  - They are unnested by definition.
  - They pass the same filters as every pool (side, draw floor, BAND/FAR tag, nearest-first). So a running extreme that price is still making sits inside the draw floor and is filtered out automatically. It becomes a candidate only once price has pulled away from it, e.g. a long after a pullback targeting the running week high.
  - **Parity:** running extreme = max/min(prior-days part, today's part up to the fill).
    - The prior-days part (period start → session open) is computed once at the session open from the same 1m parquet as the completed-period list.
    - Today's part comes from the intraday `bars[ticker]` the Executor already holds at the fill, the same bars `still_unnested` prunes with.

    So there is no new live/replay mismatch beyond the one every intraday level already has.
  - **Dedupe (Q3):** a running month extreme equal to a completed week's high, or a running week extreme equal to an existing bundle level (e.g. `week_high`), merges into one row, month preferred, others as aliases.
  - **Verify during execution:** the planner reported an existing running `week_high`/`week_low` level in `bundle.levels`. Check whether `_dol_menu` / `select_target` can already pick it at the fill. If so, only the running month is new, and the running week row dedupes against the existing level.
- **Q1 refinement (operator, 2026-09-22):** only HTF rows that **pass the draw floor** suppress the projection. Without this, on a trend day making new weekly highs the running week high right at price would block the projection while itself being ineligible, leaving the side with no target again (the 09-21 failure).

**Naming, tier, side.**
- Names: `htf_week_high_20260817`, `htf_week_low_20260729`, `htf_month_high_202608` (trade date of the extreme bar). They never match `_PREV_LEVEL_RE`, `_SESSION_LEVEL_RE`, `_PREVN_RE` or `_SESSION_EXTREME_RE`.
- `tier ∈ {"htf_week", "htf_month"}`; `side` is "above" for highs and "below" for lows.
- `is_window_extreme` flags the list's max high and min low.

**Nesting.** The same-family guard needs no change. The survivors form a frontier by construction: in time order, highs strictly decrease and lows strictly increase (a test invariant).

**Dedupe against `bundle.levels`.** If a bundle MNQ level on the same side has the identical price, drop the HTF row. The bundle's own swept/suppressed treatment then governs that price.

## Wave 1 — parallel (tests first in each task)

**T1.1 `agent/facts/htf_extremes.py`.** Pure: no `paths`, no clock, no I/O.
```python
EXTREMES_START = {                                   # the ONE per-asset constant (operator, 2026-09-22)
    "MNQ": pd.Timestamp("2026-06-16 00:00", tz="America/New_York"),  # MNQ ATH (chart); includes the Jul 29 low
    "MES": pd.Timestamp("2026-06-11 00:00", tz="America/New_York"),  # MES lowest low since May 5; includes the Aug 13 ATH
}
# The start is a TRADE date: bars with trade_date(ts) >= start. The Jun 16 extreme bar
# itself must be included, so the week containing it is truncated at the start rather
# than dropped.
@dataclass(frozen=True)
class HtfExtreme:
    name: str; ticker: str; price: float; side: str   # "above"|"below"
    tier: str                                          # "htf_week"|"htf_month"
    period: str; ts: pd.Timestamp; aliases: tuple; is_window_extreme: bool
def session_as_of(trade_date) -> pd.Timestamp          # (trade_date - 1 day) 18:00 ET
def compute_unnested_extremes(frame, as_of, *, ticker, start=None) -> list[HtfExtreme]
    # start=None -> EXTREMES_START[ticker]; COMPLETED weeks/months only
def running_period_seed(frame, as_of, *, ticker) -> dict
    # {"week": {"high": (price, ts), "low": ...}, "month": {...}}: the running week/month
    # extremes over [period start, as_of), from the same 1m parquet. Fixed at the session open.
def running_extremes_at(seed, bars_today, as_of, now) -> list[HtfExtreme]
    # combine the seed with today's bars in [as_of, now) -> running week/month high+low rows
    # (tier "htf_week_running" / "htf_month_running"), deduped per Q3
    # rows start <= ts < as_of, maintenance dropped (assemble.normalize_for_derive rules),
    # completed periods only (Q5), strict-beyond drop (Q3) via suffix cummax/cummin, dedupe+aliases
def still_unnested(extremes, frame, as_of, now) -> list[HtfExtreme]
    # drop any traded strictly beyond by a bar with as_of <= ts < now
```
Performance: about 100k rows per asset; vectorized, well under 100 ms. `still_unnested` at a fill slices under a day of bars. The ~1.5 s `build_bundle` at the fill is unchanged.

## Risks / contradictions of the premise

- Q1 = P1 is what makes 09-21's T2 the Aug 17 high. Without it the projection stays D1 (insight 1).
- A far T2 is also a far plan-death level: more re-entries, and on wrong-thesis days more exposure. The operator accepts this; the §10.2 adverse band must still hold.
- Source drift: main-era vs live 1m after parquet-check repairs; the fingerprint plus the slow test detect it.
- The per-asset start dates are fixed. As time passes, older unnested extremes stay in the list until traded beyond, which is intended.
- The initial-target "85%" has no behavioural effect while `INITIAL_TARGET_ACTION = "record"`.
- MES is computed but has no consumer (audit only).
